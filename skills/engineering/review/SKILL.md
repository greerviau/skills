# review

Review a diff, branch, or PR and report ranked findings with a ship or don't-ship call.
Review that diff, not the whole codebase. Report every defect you see, including incidental ones, and say an incidental one belongs on its own branch.
This skill reviews and does not apply changes.

## Procedure

1. Scope the diff: working tree, branch against base, or GitHub PR.
2. Correctness. Read the changed code for bugs, missed cases, and broken callers.
3. Mechanical checks. Run a subagent for this in parallel with step 4:
   - Lint: run the repo's linter. Any new violation fails.
   - Tests: run the suite. Confirm the diff adds or updates tests that exercise the change.
   - Test-first: run `scripts/tests_fail_on_base.sh <base> '<test paths>' -- <test command>`. Each added test must fail or error on the base. Skip documentation-only, formatting-only, and rename-only changes.
   - Flakiness: grep added tests for unseeded `random`, real clocks (`now()`, `sleep`), order dependence, and un-stubbed network.
   - Attribution: `git log <base>..HEAD --format='%an <%ae>%n%b'` and the PR body show no co-author trailer or "generated by" note.
   - Repo rules: check the diff against the repo's `CODING-STANDARDS.md` and `UBIQUITOUS-LANGUAGE.md` when they exist. Grep added identifiers for abbreviations and for synonyms of glossary terms. List the comments the diff adds with `git diff <base>..HEAD | grep -E -C2 '^\+.*(#|//|/\*|--|<!--)'`, which over-collects on purpose, and settle each against the surrounding code. A comment that restates the code, carries an example, or references this repo's issue or PR number is a finding.
4. Structure. Judge with these lenses and cite the one a finding breaks:
   - Depth: a **deep module** hides substantial functionality behind a narrow interface. A pass-through wrapper adds a name and no depth.
   - Information hiding: a fact every caller must know to call something safely is a leak. A leak repeated across callers means the boundary is misplaced.
   - Seam: tests attach at the real entry point, where behavior can be substituted without editing the code behind it. A seam inside a helper tests mechanics, and one only at the process boundary forces every test to drive the whole system.
   - Error elimination: ask whether the precondition that produces an error can be made impossible before accepting a new error branch.
   - Smallest sufficient change: the change fully solves the problem with the least new structure. A change that only patches the symptom fails.
   - Reuse: an existing mechanism is extended before a parallel one is added.
   - New concepts: when a concept enters the design, the interfaces around it are re-derived instead of keeping the old shape for compatibility.
   - Navigability: a concept lives in one place under its glossary name, and code that changes together lives together.
5. Conformance. Find the originating issue or spec: a linked issue, a spec path in the PR body, or one the user supplies. When none resolves, write "no originating spec located, conformance not assessed" and skip this step. Never reconstruct a spec from the diff. Otherwise report scope drift, missing requirements, and out-of-scope additions.
6. Report findings most severe first, one or two sentences each naming the location and the fix. Include no summary of the diff, no list of checks that passed, and no closing restatement. End with the ship or don't-ship call.
   When no user can answer and the review runs as a gate, emit a machine-readable verdict followed by the ranked findings.
