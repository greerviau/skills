# open-pr

Write a pull request's title and body, then create it.

## Procedure

1. Diff against the base to see what changed. The title and body describe the branch as it stands, not how it got there.
2. Title: conventional-commit form, `feat(...)` or `fix(...)`, with a concise scope and summary, such as `fix(worktree): keep worktree alive until PR merges`.
3. Link the related issue whenever one exists.
   Use a closing reference in the body such as `Fixes #123` when the PR should close it.
   A same-repository reference closes the issue when the PR merges into the default branch; the branch name alone does not.
   Use `Fixes owner/repo#123` for another repository, and `Related to #123` when the PR should not close it.
   Link a spec, plan, or other file only when it is committed and has a remote URL that PR readers can access.
   Do not link a local path, an uncommitted file, or an unpushed branch. Summarize the relevant details in the PR when no readable URL exists.
4. Find a matching PR template in the repository root, `.github/`, `docs/`, or `.github/PULL_REQUEST_TEMPLATE/`.
   Use its section order and prompts, retain template-specific sections, and omit standard sections that have no useful content for this PR.
   Format standard sections with the built-in template's headings and keep the Evidence format below when you include Evidence.
   When no matching template exists, read [references/pr-template.md](references/pr-template.md) and fill it in.
   - Problem / request: the problem or requested feature and what this PR does about it.
   - Changes: a short summary of what was done, grouped instead of file by file. When the PR changes how components interact, a state machine, or a data model, include a mermaid diagram of the result, taken from the spec when it has one.
   - Include Evidence when screenshots, output, or another concrete artifact helps show the change. Omit it when the change has no useful before-and-after evidence, such as a new skill or other text-only addition.
     When included, use this exact structure, including when a repo template exists:
     ```markdown
     ## Evidence
     ### Before
     [Previous behavior or state.]
     ### After
     [New behavior or state, with evidence.]
     ```
     Keep Before and After as separate subsections, not list items or inline labels. For a visual change, include before-and-after screenshots when the app can be run and captured. For other changes, include relevant command output or test results when they show the change. When useful evidence cannot be captured, state what blocked it and give the strongest verification you have. Never claim verification you did not perform.
     Choose the content for each subsection based on what demonstrates the change. Prefer concise bullet points that make behavior differences clear, and include screenshots, output, or command results when they provide stronger evidence.
   - Testing: include this section when you ran tests or when relevant tests exist but were not run. List test results, or say which relevant tests were not run and why. Omit it when no meaningful test applies.
   - Additional testing required: include this section only when a reviewer or QA needs to run specific tests.
   - Regressions: include this section only when there are known or plausible regressions to watch for.
5. Keep it evergreen and short:
   - The body stays accurate as the branch changes and holds no volatile details such as version bumps or transient counts.
   - No AI attribution: no "generated by" note in the body and no agent co-author line in commits.
   - Aim for about 200 words and rarely exceed 400. Check with `wc -w`, because authors read their own drafts as short. Leave diagram source out of the count.
   - Cut what the diff already shows: file walkthroughs, signatures, line counts, quoted code. State each fact once. Link an accessible spec or issue for depth.
6. Open the PR with the title and body, for example with `gh pr create`.
